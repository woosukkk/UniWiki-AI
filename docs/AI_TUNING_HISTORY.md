# AI 검색 및 답변 조정 이력

## 목적

UniWiki-AI의 AI는 사용자가 공식 문서의 제목을 정확히 입력하지 않아도 질문 의도를 파악하고, 실제 위키 문서를 근거로 답변과 출처를 함께 반환해야 한다. 이 문서는 초기 구현에서 현재 운영 방식까지 검색, 프롬프트, 점수 계산 및 데이터 반영 방식이 어떻게 바뀌었는지 정리한다.

## 기본 구현

초기 흐름은 다음과 같았다.

```text
사용자 질문
→ 질문 원문을 임베딩
→ 벡터 유사도 상위 문서 조회
→ 조회 청크를 LLM 프롬프트에 전달
→ 답변과 출처 반환
```

기본 검색은 질문 문장과 문서 청크의 의미적 유사도에 크게 의존했다. 사용자가 문서에 사용된 표현을 정확히 입력하면 잘 동작했지만, `졸업하려면 뭐 필요해?` 같은 구어체 질문은 `졸업 이수학점`, `수강편람`, `교과과정` 문서보다 단순히 졸업이라는 단어가 포함된 현장실습 공지를 먼저 찾을 수 있었다.

## 검색 후보 확대

운영 초기에는 벡터 검색 결과와 전체 문서의 어휘 검색 결과를 합쳤다. 정확한 제목을 찾는 데는 유리했지만 질문마다 Chroma 전체 청크를 애플리케이션 메모리에 적재해, 문서가 늘어날수록 Railway 컨테이너가 종료되는 문제가 있었다.

현재는 검색 메모리 상한을 두고 다음 순서로 처리한다.

```text
벡터 유사도 상위 후보(최대 60개)
→ 후보 안에서 제목·본문 어휘 점수 계산
→ 혼합 재정렬
→ 같은 위키와 같은 제목 중복 제거
→ 요청한 top-k만 반환
```

벡터 검색은 표현이 달라도 의미가 가까운 문서를 찾고, 제한된 후보의 어휘 점수는 학과명·연도·제도명처럼 정확히 일치해야 하는 정보를 보완한다. `우아한테크코스`, `그리디` 같은 고유명사가 벡터 후보 밖에 있어도 찾을 수 있도록 Chroma의 서버 측 본문 포함 필터를 사용하고, 일치 청크는 최대 20개까지만 후보에 합친다. 답변 문맥을 확장할 때도 전체 컬렉션을 다시 읽지 않고 최종 선택된 위키 ID의 청크만 조회한다. 임베딩 동기화 배치도 4개로 제한해 수집 직후의 순간 메모리 사용량을 낮췄다.

## 한국어 조사 처리

초기 어휘 비교에서는 `장학금은`, `수강편람과`처럼 조사가 붙은 단어가 제목과 일치하지 않았다. 검색 토큰에서 대표적인 한국어 조사를 제거해 원형을 비교하도록 변경했다.

단, 단순히 마지막 글자를 제거하면 `소프트웨어학과`가 `소프트웨어학`으로 바뀌는 문제가 있었다. 현재는 다음 예외를 둔다.

- `학과`로 끝나는 단어의 `과`는 보존한다.
- `교과`로 끝나는 단어의 `과`도 보존한다.
- `수강편람과`처럼 실제 조사로 사용된 경우에만 `과`를 제거한다.

## 질문 의도 확장

구어체 질문을 공식 자료의 용어로 연결하기 위해 검색 직전에 의도별 확장어를 붙인다. 사용자에게 반환되는 질문 원문은 바꾸지 않고 검색에만 확장 문장을 사용한다.

졸업 관련 표현:

```text
입력: 소프트웨어학과 졸업하려면 뭐 필요해?

검색용 확장:
소프트웨어학과 졸업하려면 뭐 필요해?
졸업 요건
졸업 이수 학점
전공필수
교양필수
수강편람
교과과정
```

수강신청 관련 표현에는 `수강신청`, `수강편람`, `강의시간표`를 연결한다. 새로운 학사 의도를 추가할 때도 `_expand_query`에 같은 방식으로 대표 공식 용어를 등록한다.

## LLM 검색어 재작성

고정된 동의어만으로는 `공고/공지`, 한글·영문 고유명사처럼 계속 늘어나는 표현 차이를 처리하기 어렵다. 현재 RAG 답변은 검색 전에 저비용 LLM 호출로 질문을 공식 문서 검색 표현으로 재작성한다.

```text
장학금 공고 어디서 봐?
→ 원문을 보존
→ 장학금 공지, 장학생 모집 안내 등 검색 표현 생성
→ 원문과 재작성 문장을 결합해 검색
```

재작성기는 답변을 만들지 않으며 고유명사, 학과, 연도와 학기를 보존한다. 동일 질문의 재작성 결과는 최대 256개까지 프로세스 메모리에 캐시한다.

## 대화형 불필요 단어 제거

`뭐`, `필요해`, `어떻게`, `돼`, `되나요`, `하려면` 등은 질문의 말투를 구성하지만 어떤 문서를 선택할지 결정하는 핵심어는 아니다. 이 단어가 어휘 점수의 분모를 키워 핵심 문서 점수를 낮추지 않도록 검색 토큰에서 제외한다. `졸업하려면`처럼 핵심어와 종결 표현이 결합된 토큰도 별도로 처리한다.

## 혼합 점수와 제목 우선순위

현재 기본 혼합 점수는 다음 구조다.

```text
모든 검색 후보:
  vector_score × 0.3 + lexical_score × 0.8

어휘 일치가 없으면 `lexical_score`는 0이며, 최종 점수는 1.0을 넘지 않는다.
```

어휘 점수에는 제목의 완전 일치, 긴 한국어 토큰의 제목 일치, 부분 일치, 본문 일치, 질문 연도와 제목 연도 일치가 반영된다. 제목은 본문보다 높은 점수를 받는다.

의도가 분명한 경우 다음 제목 보정도 적용한다.

- 질문과 제목에 모두 `졸업`이 있으면 `+0.25`
- 질문에 포함된 `○○학과`가 제목에도 있으면 `+0.15`

이 보정으로 `소프트웨어학과 졸업하려면 뭐 필요해?`는 졸업을 언급한 현장실습 공지보다 `2026 소프트웨어학과 졸업 이수학점 안내`를 먼저 반환한다.

## RAG 답변 프롬프트 원칙

최종 답변 생성은 검색된 위키 청크만 근거로 사용한다.

- 검색 문서에 없는 사실을 만들어내지 않는다.
- 답변과 함께 실제 위키 ID 및 링크를 출처로 반환한다.
- 충분한 근거가 없으면 자료가 부족하다고 명시한다.
- 여러 청크가 같은 위키에 속하면 필요한 범위까지 확장하되 출처는 위키 단위로 중복 제거한다.
- 졸업요건처럼 연도와 학과가 중요한 질문은 해당 연도·학과 제목을 우선한다.

근거 점수는 두 단계로 처리한다.

- `0.35` 이상: 충분한 근거로 답변하고 `grounded: true`를 반환한다.
- `0.20` 이상 `0.35` 미만: 문서에 직접 적힌 내용만 제한적으로 소개하고 `grounded: false`와 출처를 반환한다.
- `0.20` 미만: 답변 근거가 부족하다고 반환한다.

LLM도 `SUPPORTED` 또는 `INSUFFICIENT` 판정을 반환하며, 검색 점수가 부분 근거 구간이면 모델의 판정과 관계없이 제한적 답변으로 표시한다.

## 함께 만든 위키 반영

관리자가 질문의 답변을 채택하면 질문과 답변을 기반으로 `함께 만든 위키` 문서가 생성된다. 생성 또는 갱신된 위키는 벡터 동기화 대상에 포함되므로 공식 위키와 동일하게 AI 검색 후보가 된다.

```text
질문 게시물 + 채택 답변
→ 함께 만든 위키 생성/갱신
→ 벡터 동기화 작업 등록
→ AI 벡터 저장소 반영
→ 이후 질문의 검색 출처로 사용
```

질문의 상태를 `답변 완료`로 표시하는 것만으로는 함께 만든 위키가 생성되지 않는다. 위키 생성은 답변 채택 또는 관리자 선정 절차를 거쳐야 한다.

## 기본형과 최종형 비교

```text
[기본]
질문 원문 임베딩
→ 벡터 유사도만 사용
→ 상위 청크를 그대로 LLM에 전달

[최종]
질문 원문
→ LLM 검색어 재작성 및 학사 의도 확장
→ 조사 및 구어체 노이즈 정규화
→ 벡터 후보 + 어휘 후보 수집
→ 벡터 0.3 / 어휘 0.8 혼합 재정렬
→ 연도·학과·졸업 의도 제목 우선 보정
→ 위키 중복 제거 및 관련 청크 확장
→ 공식 위키와 함께 만든 위키를 함께 근거로 사용
→ 충분/부분/부족 근거 판정
→ 근거 기반 답변과 실제 출처 반환
```

## 현재 검증 사례

- `소프트웨어학과 졸업 조건이 어떻게 돼?`
- `소프트웨어학과 졸업하려면 뭐 필요해?`
- `졸업 요건을 알려줘`

위 표현은 모두 수강편람 및 교과과정 기반 졸업요건 문서로 연결된다. 운영 검증에서는 `2026 소프트웨어학과 졸업 이수학점 안내`가 첫 번째 출처로 반환됐다.

검색 로직을 변경할 때는 `ai/tests/test_search_api.py`와 `ai/tests/test_rag_api.py`를 함께 실행하고, 관련 문서가 단순 의미 유사 문서보다 먼저 오는지를 순위 단위로 검증해야 한다.

## 2026-08-10 최종 운영 안정화

과거 전체 Chroma 레코드를 애플리케이션 메모리로 읽는 방식은 고유명사 검색률은 높였지만 Railway 컨테이너가 `Killed` 되는 원인이 됐다. 현재는 다음의 제한된 후보만 사용한다.

```text
벡터 후보 최대 60개
+ Chroma 서버 측 정확 키워드 후보 최대 20개
→ 고유명사 후보 우선 병합
→ 최종 위키 ID의 청크만 조회
```

이 방식으로 우아한테크코스·그리디 검색을 복구하면서 전체 컬렉션 스캔을 제거했다. 연도·학기 신호가 있는 질문은 최신 문서를 우선한다.

띄어쓰기가 문서 제목과 다른 경우를 위해 인접 토큰 결합 후보도 만든다. 예를 들어 `교내 장학금`은 원래 토큰과 함께 `교내장학금`을 정확 키워드 후보로 조회한다.

출처 우선순위는 질문 의도에 따라 적용한다. 후기·팁·취업·프로젝트·경험 질문은 함께 만든 위키에 가산점을 주고, 일정·규정·장학금·졸업·수강 질문은 공식 위키에 더 큰 가산점을 준다. 어느 쪽도 아닌 질문은 점수가 비슷할 때 함께 만든 위키가 먼저 오도록 작은 기본 가산점만 적용한다.

- 같은 위키의 대기·실패 UPSERT 작업은 새 행 대신 기존 작업을 갱신한다.
- 완료 작업은 payload를 비우고 오래된 작업은 작은 트랜잭션으로 배치 삭제한다.
- 공식 자료 재적재는 공식 작성자 문서만 대상으로 하며 고정 문서 1·2·3과 사용자·질문 데이터는 보존한다.

운영 복구에서는 공식 위키 5,754건의 기존 벡터와 연결 데이터를 정리하고 2024년 이후 자료 재수집을 시작했다. 초기화 플래그는 반복 삭제를 막기 위해 정리 직후 비활성화했다.
