# UniWiki-AI AI 처리 기술 및 구현 방식

## 1. AI 기능의 목표

UniWiki-AI의 AI는 일반적인 지식으로 자유롭게 답하는 챗봇이 아니라, 저장된 대학 위키를 검색한 뒤 해당 자료만 근거로 답하는 RAG 서비스다.

```text
사용자 질문
→ 관련 위키 검색
→ 근거 문맥 구성
→ LLM 답변 생성
→ 실제 위키 출처 반환
```

핵심 목표는 답변의 유창함보다 학교 자료에 근거한 정확성과 출처 추적 가능성이다.

## 2. 사용 기술

| 구분 | 기술 | 사용 목적 |
|---|---|---|
| 언어 | Python | AI 서비스와 데이터 처리 |
| API | FastAPI | 검색·벡터·RAG HTTP API |
| 서버 | Uvicorn | ASGI 애플리케이션 실행 |
| 데이터 검증 | Pydantic | 요청·응답 모델 검증 |
| 임베딩 | FastEmbed | 다국어 문장 임베딩 생성 |
| 기본 임베딩 모델 | paraphrase-multilingual-MiniLM-L12-v2 | 한국어 지원과 낮은 메모리 사용량 균형 |
| 벡터 DB | ChromaDB | 위키 청크와 임베딩 영속 저장 |
| 수치 처리 | NumPy | 임베딩 벡터 처리 |
| LLM | OpenAI Responses API | 검색 근거를 이용한 최종 답변 생성 |
| HTTP | HTTPX | OpenAI 및 서비스 간 통신 |
| 테스트 | Pytest, FastAPI TestClient | 검색·RAG·벡터 API 검증 |
| 배포 | Docker, Railway Volume | AI 서버와 벡터 DB 영속화 |

## 3. 전체 AI 아키텍처

```text
React
  ↓ 질문
Spring Boot
  ↓ 내부 AI 요청
FastAPI AI 서비스
  ├── Query Expansion
  ├── Embedder
  ├── Hybrid Search
  ├── ChromaDB
  └── RAG Service
          ↓
    OpenAI Responses API
```

프론트엔드가 AI 서비스나 OpenAI를 직접 호출하지 않는다. 백엔드가 요청 경계가 되어 인증, 오류 처리와 AI 서비스 주소를 관리한다.

## 4. 위키 벡터화 과정

위키는 문서 전체를 하나의 벡터로 저장하지 않고 일정 크기의 청크로 분할한다.

기본 파라미터:

| 환경 변수 | 기본값 | 의미 |
|---|---:|---|
| `CHUNK_MAX_CHARS` | 800 | 청크 하나의 최대 문자 수 |
| `CHUNK_OVERLAP_CHARS` | 120 | 앞뒤 청크가 공유하는 문맥 |
| `CHROMA_COLLECTION` | `uniwiki_wiki_chunks` | Chroma 컬렉션 이름 |

```text
위키 제목 + 본문
→ 문단과 길이를 고려해 청크 분리
→ 인접 청크 120자 중첩
→ 제목과 청크 내용 임베딩
→ wikiPostId, categoryId, chunkIndex와 함께 ChromaDB 저장
```

중첩 영역을 두는 이유는 문장이 청크 경계에서 잘려 핵심 맥락이 사라지는 문제를 줄이기 위해서다.

## 5. 가벼운 임베딩 모델 선택

초기에는 더 큰 임베딩 모델을 사용할 수 있지만 Railway의 제한된 메모리에서는 모델 로딩과 검색 과정이 서버 안정성에 영향을 줄 수 있다. 현재 기본 모델은 다국어 MiniLM 계열로 설정했다.

```text
sentence-transformers/paraphrase-multilingual-MiniLM-L12-v2
```

선택 기준:

- 한국어와 영어를 함께 처리
- 대형 임베딩 모델보다 작은 메모리 사용량
- CPU 환경에서도 실행 가능한 속도
- 운영 볼륨에 벡터를 영속 저장해 재시작 시 전체 재생성 최소화

## 6. 질문 재작성과 의도 확장

사용자는 공식 문서 제목과 같은 표현으로 질문하지 않는다. 따라서 LLM이 원문의 고유명사·학과·연도·학기를 보존하면서 동의어와 행정 용어를 포함한 검색 문장을 만든다. 원문과 재작성 문장을 함께 검색하며 동일 질문은 캐시한다.

```text
입력 질문:
소프트웨어학과 졸업하려면 뭐 필요해?

검색용 표현 추가:
졸업 요건 / 졸업 이수 학점 / 전공필수 / 교양필수
수강편람 / 교과과정
```

예를 들어 `장학금 공고`는 고정 사전 없이 문맥에 따라 `장학금 공지`, `장학생 모집 안내` 같은 표현으로 확장된다.

또한 한국어 조사를 제거해 제목 일치율을 높인다. 이때 `소프트웨어학과`의 마지막 `과`는 조사가 아니므로 보존하고, `수강편람과`의 `과`처럼 실제 조사인 경우만 제거한다.

`뭐`, `필요해`, `어떻게`, `하려면` 같은 대화형 표현은 문서 선택에 도움이 되지 않으므로 어휘 점수 계산에서 제외한다.

세부 변경 과정은 [AI_TUNING_HISTORY.md](./AI_TUNING_HISTORY.md)에 정리돼 있다.

## 7. 하이브리드 검색

벡터 검색만 사용하면 의미가 비슷한 문서는 잘 찾지만 학과명, 연도, 제도명 같은 정확한 조건이 약해질 수 있다. 이를 보완하기 위해 벡터 검색과 어휘 검색을 결합한다.

```text
검색 질문
├── 임베딩 기반 벡터 후보
└── 제목·본문 어휘 일치 후보
          ↓
      후보 합치기
          ↓
      혼합 점수 재정렬
          ↓
      위키 단위 중복 제거
```

기본 검색 파라미터:

| 항목 | 값 |
|---|---:|
| 기본 검색 결과 | 5개 |
| 벡터 후보 | top-k의 6배, 최소 30개 |
| 벡터 점수 가중치 | 0.3 |
| 어휘 점수 가중치 | 0.8 |
| 졸업 의도 제목 보정 | +0.25 |
| 동일 학과 제목 보정 | +0.15 |

어휘 점수에는 제목 완전 일치, 긴 한국어 단어의 제목 일치, 본문 일치와 질문 연도 일치가 포함된다. 최종 점수는 1.0을 넘지 않도록 제한한다.

## 8. 검색 결과 확장

첫 검색에서는 관련 문서를 찾는 것이 목표이므로 위키별 대표 청크를 우선 선택한다. RAG 문맥을 만들 때는 선택된 위키의 인접 청크를 최대 8개까지 다시 가져온다.

```text
대표 청크로 관련 위키 선택
→ 같은 wikiPostId의 청크를 순서대로 확장
→ 전체 문맥 길이 제한 안에서 결합
```

이를 통해 검색 결과 수를 과도하게 늘리지 않으면서 긴 수강편람이나 교과과정 문서의 세부 내용을 답변에 사용할 수 있다.

## 9. RAG 답변 생성

기본 RAG 파라미터:

| 환경 변수 | 기본값 | 의미 |
|---|---:|---|
| `RAG_TOP_K` | 5 | 답변에 사용할 상위 문서 수 |
| `RAG_MIN_SCORE` | 0.35 | 근거로 인정할 최소 검색 점수 |
| `RAG_PARTIAL_MIN_SCORE` | 0.20 | LIMITED SOURCES로 활용할 최소 점수 |
| `RAG_MAX_CONTEXT_CHARS` | 12000 | LLM에 전달할 최대 문맥 길이 |
| `OPENAI_MAX_OUTPUT_TOKENS` | 1000 | 최대 답변 출력량 |
| `OPENAI_TIMEOUT_SECONDS` | 30 | LLM 요청 제한 시간 |

```text
검색 결과
→ 최소 점수 미만 제거
→ 관련 위키의 청크 확장
→ 최대 12,000자 문맥 구성
→ 시스템 지침 + 사용자 질문 + 위키 문맥
→ OpenAI Responses API 호출
→ 답변과 출처 반환
```

프롬프트 원칙:

- 제공된 위키 문서만 근거로 사용
- 문서에 없는 사실을 추측하지 않음
- 근거가 부족하거나 충돌하면 부족하다고 명시
- 한국어로 간결하고 직접적인 답변 생성

검색 점수를 넘긴 문서가 하나도 없으면 LLM을 호출하지 않고 `근거 부족` 응답을 반환한다.

## 10. 출처 처리

LLM이 임의의 링크를 만드는 방식이 아니라 검색에 사용된 실제 위키 ID로 출처를 구성한다.

```json
{
  "answer": "...",
  "grounded": true,
  "sources": [
    {
      "wikiPostId": 47,
      "title": "2026 소프트웨어학과 졸업 이수학점 안내",
      "url": "/api/wiki-posts/47"
    }
  ]
}
```

같은 위키의 여러 청크가 사용돼도 출처 목록에서는 위키 ID와 제목을 기준으로 중복 제거한다.

## 11. 공식 위키와 함께 만든 위키

AI 검색 대상은 두 가지다.

- 공식 위키: 세종대학교 공식 사이트와 첨부파일 기반
- 함께 만든 위키: 질문 게시판에서 관리자가 선정한 질문·답변 기반

```text
공식 자료 또는 선정된 질문·답변
→ 백엔드 위키 저장
→ 벡터 UPSERT 작업 등록
→ AI 서비스가 청크와 임베딩 갱신
→ 다음 질문부터 검색 근거로 사용
```

질문 상태가 `답변 완료`인 것만으로는 위키가 되지 않는다. 관리자가 위키로 선정해야 함께 만든 위키가 생성되고 벡터 검색에도 반영된다.

## 12. 장애와 데이터 일관성 처리

- OpenAI 키가 없으면 설정 오류로 구분
- LLM 시간 초과와 제공자 오류를 별도 예외로 처리
- 벡터 동기화 실패는 백엔드 작업 큐에 남겨 재시도
- ChromaDB는 Railway Volume에 저장해 재배포 후에도 유지
- 위키 삭제 시 대응하는 벡터도 DELETE 작업으로 제거
- 테스트에서는 가짜 임베더와 LLM을 사용해 외부 API 없이 순위와 근거 처리를 검증

## 13. 기본 방식과 최종 방식

```text
[기본]
질문 원문 임베딩
→ 벡터 유사도 상위 문서
→ LLM 답변

[최종]
질문 의도 확장
→ 한국어 조사·구어체 정규화
→ 벡터 후보 + 어휘 후보
→ 학과·연도·제목 우선 혼합 재정렬
→ 관련 위키 청크 확장
→ 최소 근거 점수 검사
→ 공식 위키와 함께 만든 위키 기반 답변
→ 실제 위키 ID 출처 반환
```

## 14. 발표용 핵심 요약

> AI 서비스는 FastAPI, FastEmbed, ChromaDB와 OpenAI Responses API로 구성한 RAG 시스템입니다. 위키를 800자 단위로 나누고 120자를 중첩해 벡터화하며, 한국어 질문은 조사 제거와 학사 의도 확장을 거칩니다. 벡터 유사도와 제목·본문 어휘 점수를 함께 사용해 학과와 연도 조건을 보존하고, 최소 점수 이상의 실제 위키 문서만 LLM에 전달합니다. 답변에는 검색에 사용된 위키 ID를 출처로 제공하며, 근거가 없으면 답변을 생성하지 않습니다.

## 15. 시연 순서 제안

1. `졸업 요건`과 `졸업하려면 뭐 필요해?`를 각각 질문
2. 두 질문이 같은 수강편람 기반 위키를 찾는지 비교
3. 답변의 첫 출처가 해당 학과·연도 문서인지 확인
4. 관리자가 질문을 함께 만든 위키로 선정
5. 벡터 동기화 후 관련 질문에서 새 위키가 출처로 나오는지 확인
6. 근거가 없는 질문에서 근거 부족 응답 확인
