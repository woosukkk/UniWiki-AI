# UniWiki-AI 백엔드 기술 및 구현 방식

## 1. 백엔드의 역할

UniWiki-AI 백엔드는 사용자, 위키, 질문과 답변, 추천, 관리자 기능을 처리하는 중심 API 서버다. 또한 공식 학교 자료와 커뮤니티 데이터를 저장하고, 변경된 위키를 AI 벡터 저장소에 반영하는 연결 지점 역할을 한다.

```text
프론트엔드
→ Spring Boot REST API
→ MySQL
→ AI 서비스 / 공식 자료 수집기
```

## 2. 사용 기술

| 구분 | 기술 | 사용 목적 |
|---|---|---|
| 언어 | Java 21 | 백엔드 비즈니스 로직 구현 |
| 프레임워크 | Spring Boot 3.4.5 | REST API와 애플리케이션 실행 환경 |
| 웹 | Spring MVC | Controller 기반 HTTP 요청 처리 |
| 데이터 접근 | Spring Data JPA | 엔티티 매핑과 Repository 구현 |
| 운영 DB | MySQL | 사용자·위키·질문·수집 데이터 저장 |
| 로컬·테스트 DB | H2 | 테스트 및 제한적인 로컬 실행 지원 |
| 인증 | JWT, JJWT | 로그인 상태와 사용자 권한 확인 |
| 검증 | Jakarta Validation | 요청 DTO의 입력값 검증 |
| API 문서 | Springdoc OpenAPI | Swagger UI 기반 API 확인 |
| HTML 분석 | Jsoup | 학교 공지 및 본문 수집 |
| 첨부파일 | PDFBox, Apache POI | PDF 및 Excel 문서 텍스트 추출 |
| 브라우저 자동화 | Selenium | 동적 페이지 수집 지원 |
| 테스트 | JUnit 5, Spring Boot Test | 서비스와 API 동작 검증 |
| 배포 | Docker, Railway | 백엔드와 MySQL 운영 |

## 3. 계층형 구조

백엔드는 공통 계층형 구조를 사용한다.

```text
controller → service → repository → database
                 ↓
             entity / dto
```

- `controller`: URL, HTTP 메서드, 요청 검증과 응답 형식 담당
- `service`: 트랜잭션, 권한 확인, 핵심 비즈니스 규칙 처리
- `repository`: JPA 기반 DB 조회와 갱신
- `entity`: DB 테이블 매핑과 도메인 상태 변경
- `dto`: 외부 요청·응답 형식 분리
- `config`: JWT 인터셉터, CORS, 시작 작업과 MVC 설정

엔티티를 API 응답으로 직접 노출하지 않고 DTO로 변환해 DB 구조와 외부 API를 분리했다.

## 4. 주요 도메인

### 위키

- 위키 작성·조회·수정·삭제
- 제목과 본문 검색
- 카테고리와 출처 구분
- 공식 위키와 함께 만든 위키 관리
- 추천 수와 데이터 신뢰도 집계
- 생성·수정·삭제 시 AI 벡터 동기화 작업 등록

### 질문과 답변

- 질문 게시물과 답변 작성
- 질문·답변 추천
- 질문 작성자 또는 관리자의 답변 채택
- 답변이 채택되면 질문을 `CLOSED`로 전환
- 관리자가 질문이나 답변을 함께 만든 위키로 선정
- 수집 게시물에 댓글이 있으면 답변으로 저장하고 완료 상태로 전환

### 사용자와 관리자

- 회원가입과 로그인
- 일반 사용자와 관리자 역할 구분
- 관리자 대시보드
- 질문·답변의 위키 선정
- 공식 출처 수집과 처리 상태 확인

## 5. JWT 인증 방식

로그인 성공 시 서버가 JWT를 발급한다. 프론트엔드는 이후 요청에 다음 헤더를 추가한다.

```http
Authorization: Bearer {JWT}
```

백엔드 처리 과정은 다음과 같다.

```text
요청
→ JwtInterceptor가 토큰 검증
→ 사용자 ID 추출
→ LoginUserIdResolver
→ Controller의 @LoginUserId Long userId에 전달
→ Service에서 작성자·관리자 권한 확인
```

클라이언트가 전달한 작성자 ID를 신뢰하지 않고, 검증된 토큰의 사용자 ID를 기준으로 작성과 수정 권한을 판단한다.

## 6. 공식 자료 수집 파이프라인

세종대학교 공식 사이트를 등록된 출처로 관리하고 변경된 자료만 처리한다.

```text
공식 출처 목록
→ 주기적 목록·본문 확인
→ 신규 또는 변경 문서 판별
→ 원문과 메타데이터 저장
→ 첨부파일 다운로드
→ HTML / PDF / Excel 텍스트 추출
→ 주제별 위키 생성 또는 갱신
→ 벡터 동기화 작업 등록
```

공식 자료는 출처 URL, 수집 상태, 첨부파일 추출 상태를 별도 엔티티로 관리한다. 같은 주제의 공지가 반복될 때는 무조건 새 위키를 만들지 않고 주제 키를 이용해 기존 위키에 통합할 수 있게 구성했다.

## 7. 커뮤니티 데이터 처리

외부 커뮤니티 데이터는 공식 자료와 구분해 원시 데이터로 먼저 저장한다.

```text
수집 게시물
→ 원시 게시물 저장
→ 욕설 제거 및 내용 정리
→ 질문 게시판 게시물 생성
→ 댓글을 답변으로 저장
→ 추천 수를 외부 추천 수로 보존
→ 관리자 선정 시 함께 만든 위키 생성
```

공식 자료는 검증된 출처 중심이고, 커뮤니티 자료는 질문·답변과 관리자 선정을 거치도록 처리 경로를 분리했다.

## 8. 벡터 동기화 방식

백엔드는 위키 저장 트랜잭션에서 AI 서비스를 무조건 즉시 호출하지 않는다. 먼저 동기화 작업을 DB에 저장한다.

```text
위키 생성·수정·삭제
→ wiki_vector_sync_jobs에 UPSERT 또는 DELETE 작업 저장
→ 스케줄러가 대기 작업 조회
→ AI 벡터 API 호출
→ 성공 시 COMPLETED
→ 실패 시 FAILED로 기록 후 제한 횟수만큼 재시도
```

이 방식은 AI 서비스가 잠시 중단돼도 위키 저장 자체가 실패하지 않게 하며, 실패한 동기화를 다시 처리할 수 있게 한다. 즉, DB를 원본 데이터로 두고 벡터 DB는 재구성 가능한 검색 인덱스로 사용한다.

## 9. 데이터 일관성과 트랜잭션

- 조회 서비스에는 읽기 전용 트랜잭션 적용
- 작성·수정·삭제·채택에는 쓰기 트랜잭션 적용
- 답변 채택 시 질문을 비관적 잠금으로 조회해 중복 채택 방지
- 같은 질문에 이미 채택된 답변이 있으면 충돌 응답 반환
- 위키 선정과 벡터 동기화 작업을 서비스 계층에서 함께 처리

## 10. 발표용 핵심 요약

> 백엔드는 Java 21과 Spring Boot로 구현했으며, MySQL을 원본 데이터 저장소로 사용했습니다. JWT 인터셉터를 통해 인증을 공통 처리하고, Controller-Service-Repository 계층을 분리했습니다. 학교 공식 사이트의 HTML과 PDF·Excel 첨부파일을 수집해 위키로 구성하며, 위키 변경은 작업 큐 형태로 AI 서비스에 동기화합니다. 질문 게시판의 답변은 관리자 선정 과정을 거쳐 함께 만든 위키와 AI 검색 자료로 연결됩니다.

## 11. 시연 순서 제안

1. 로그인 후 JWT 인증 요청 확인
2. 위키 목록과 상세 페이지 조회
3. 질문 작성 및 답변 등록
4. 관리자 계정으로 답변 채택 또는 위키 선정
5. 함께 만든 위키 생성 확인
6. 같은 내용을 AI에 질문해 새 위키가 출처로 사용되는지 확인
