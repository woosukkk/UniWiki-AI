# UniWiki-AI 포트폴리오

## 프로젝트 소개

UniWiki-AI는 세종대학교의 여러 홈페이지와 첨부파일에 흩어진 대학생활 정보를 읽기 좋은 위키로 정리하고, 실제 위키 문서를 근거로 AI 답변을 제공하는 지식 플랫폼입니다. 공식 자료와 학생 질문·답변을 하나의 지식 순환 구조로 연결해 사용자가 정보를 찾고, 답을 얻고, 원문으로 검증할 수 있도록 설계했습니다.

## 해결하려는 문제

- 학교 정보가 여러 홈페이지와 학과 게시판에 분산되어 있습니다.
- 졸업요건·장학·수강 정보의 세부 내용이 PDF, Excel, DOCX 첨부파일 안에 있어 검색하기 어렵습니다.
- 최신 공지와 오래된 공지가 섞여 있어 사용자가 최신성을 직접 판단해야 합니다.
- 일반 생성형 AI의 답변은 빠르지만 답변 근거가 된 학교 문서를 확인하기 어렵습니다.
- 학생들의 유용한 답변과 경험이 일회성 게시글로 소멸됩니다.

## 주요 사용자 기능

- 연도·학기·카테고리별 공식 위키 검색 및 원문 출처 확인
- 질문 작성, 답변, 추천, 채택과 답변 완료 상태 관리
- 관리자 선정을 통한 `함께 만든 위키` 축적
- 공식 위키와 함께 만든 위키를 함께 검색하는 RAG 챗봇
- 수집량·최신성·출처 신뢰도를 보여주는 데이터 지도
- 공식 출처 수집 상태와 벡터 동기화 상태를 확인하는 관리자 기능

## 전체 시스템 구조

```text
공식 홈페이지·첨부파일
        │ 수집·정제
        ▼
Spring Boot ───────────── MySQL
     ▲  │ REST API / JWT      │ 원본 데이터
     │  │ vector sync jobs    │
React  ▼                      ▼
+ Vite FastAPI ─────────── ChromaDB
     │          검색 문맥
     └────────── OpenAI Responses API
```

프론트엔드는 데이터베이스나 OpenAI API에 직접 접근하지 않습니다. Spring Boot가 인증과 비즈니스 트랜잭션을 담당하고, FastAPI가 위키 동기화·검색·근거 기반 답변 생성을 담당합니다. MySQL은 원본 데이터 저장소, ChromaDB는 재구성 가능한 검색 인덱스로 사용합니다.

## 사용 기술

| 영역 | 기술 | 역할 |
|---|---|---|
| Frontend | React 19, Vite 8, React Router 7, Axios | SPA, 인증 상태, 위키·질문·AI 화면 |
| Backend | Java 21, Spring Boot 3.4.5, Spring Data JPA | REST API, 인증, 트랜잭션, 수집 파이프라인 |
| Database | MySQL, H2 | 운영 데이터와 테스트 데이터 저장 |
| AI | Python, FastAPI, FastEmbed, ChromaDB, OpenAI Responses API | 임베딩, 하이브리드 검색, RAG 답변 |
| Collection | Jsoup, Selenium, PDFBox, Apache POI | HTML과 첨부파일 수집·텍스트 추출 |
| Deployment | Vercel, Railway, Docker | 서비스별 독립 배포와 영속 저장소 운영 |

## 본인이 구현한 핵심 영역

프로젝트 기획과 총괄, 서비스 간 기능 연동, 운영·배포를 중심으로 구현했습니다. 특히 공식 자료 수집에서 위키 생성, 벡터 동기화, AI 검색까지 이어지는 전체 흐름을 통합하고, 실제 운영 환경에서 발생한 메모리 및 검색 품질 문제를 분석해 안정화했습니다. 구체적인 팀원별 기여 범위는 발표자료의 개인정보 공개 동의 확인 후 공개할 예정입니다.

## 공식 자료 수집 및 위키 생성 과정

```text
등록된 공식 출처
→ 목록·본문 변경 감지
→ 원문과 첨부파일 저장
→ HTML / PDF / Excel / DOCX 텍스트 추출
→ 읽기 좋은 마크다운 위키 생성·갱신
→ 벡터 동기화 작업 등록
→ AI 검색 반영 확인
```

일반 공지는 하위 문서 한 건을 위키 한 건으로 관리하고, SW중심대학사업단·TOSC·uDream처럼 특성이 다른 출처는 통합 문서 정책을 적용합니다. 신규 네트워크 요청은 `robots.txt`와 호스트별 요청 간격을 준수하며, 2025년 이후 공식 자료를 최신성 기준으로 유지합니다.

## RAG 검색과 답변 생성 과정

사용자 질문은 한국어 조사와 대화형 불필요 단어를 정규화하고, 학사 의도와 공식 문서 표현을 보완한 뒤 검색합니다. 벡터 후보와 정확 키워드 후보를 결합하고, 관련 카테고리를 최대 5개 선택해 해당 카테고리 문서를 다시 정렬합니다. 최종 컨텍스트는 문서마다 최대 3개 청크를 라운드로빈으로 배치해 긴 문서 하나가 입력 공간을 독점하지 않도록 했습니다.

검색 결과가 최소 근거 점수를 충족할 때만 실제 위키 청크를 OpenAI Responses API에 전달합니다. 답변에는 사용된 위키 출처를 함께 제공하고, 근거가 부족하면 추측하지 않고 질문 게시판으로 연결합니다.

## Railway 메모리 문제와 해결 과정

초기 검색은 고유명사 검색률을 높이기 위해 전체 Chroma 레코드를 애플리케이션 메모리로 읽었습니다. 공식 문서가 늘면서 AI 컨테이너가 `Killed` 되는 문제가 발생했습니다.

이를 해결하기 위해 전체 컬렉션 스캔을 제거하고 벡터 후보 최대 60개와 서버 측 정확 키워드 후보 최대 20개를 우선 수집하도록 변경했습니다. 이후 질문 의도에 맞는 카테고리만 선택하고, 선택된 위키의 청크만 추가 조회했습니다. 임베딩 동기화 배치 크기도 제한하고 완료 작업의 payload와 오래된 작업을 소규모 배치로 정리해 메모리와 저장공간 사용량을 통제했습니다.

## 검색 정확도 개선 과정

- 벡터 유사도와 제목·본문 어휘 점수를 결합한 하이브리드 검색
- 한국어 조사 제거와 `학과`·`교과` 등 예외 처리
- 졸업·수강신청 등 구어체 질문을 공식 문서 용어로 확장
- 저비용 LLM 검색어 재작성으로 공고/공지와 고유명사 표현 차이 보완
- 연도·학과·질문 의도에 따른 제목 및 출처 우선순위 보정
- 카테고리 기반 전체 문서 재정렬로 종합 안내 문서 누락 방지
- 문서별 최대 3청크 라운드로빈 배치로 근거 다양성 확보

## 테스트와 배포 방식

- Backend: JUnit 5와 Spring Boot Test로 서비스·API 검증
- Frontend: Vite 프로덕션 빌드로 번들 및 라우팅 검증
- AI: Pytest와 FastAPI TestClient로 검색 순위·근거 판정·벡터 API 검증
- AI Docker 이미지 빌드 중 전체 테스트를 실행해 회귀 발생 시 배포 중단
- Vercel에 프론트엔드, Railway에 백엔드·AI·MySQL 배포
- ChromaDB는 Railway Volume에 저장해 AI 재배포 후에도 유지
- 위키 저장과 벡터 동기화를 작업 큐로 분리해 AI 장애가 원본 DB 쓰기에 영향을 주지 않도록 격리

## 프로젝트를 통해 배운 점

- RAG 품질은 후보 수보다 어떤 문서를 실제 컨텍스트에 넣는지가 더 중요합니다.
- 벡터 검색만으로는 고유명사·연도·학과처럼 정확한 일치가 필요한 질문을 안정적으로 처리하기 어렵습니다.
- 데이터베이스와 벡터 저장소의 역할을 분리하면 AI 장애를 격리하고 검색 인덱스를 재구성할 수 있습니다.
- 운영 환경의 메모리 한도와 데이터 증가 속도를 고려한 검색·동기화 설계가 필요합니다.
- 자동 수집은 수집 성공뿐 아니라 출처 정책, 최신성, 중복, 재시도, 삭제 정책까지 함께 설계해야 합니다.

## 향후 개선 사항

- 검색 품질을 질문 유형별 정량 평가셋으로 관리
- 출처별 최신성·신뢰도 점수를 검색 순위에 더 정교하게 반영
- 수집 실패와 벡터 동기화 지연을 한눈에 볼 수 있는 운영 관측성 강화
- 개인정보 공개 동의가 확인된 발표자료의 익명화 또는 공개본 제작
- 접근성 및 모바일 사용성에 대한 자동화 회귀 테스트 확대
